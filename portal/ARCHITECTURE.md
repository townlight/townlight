# Portal architecture

Townlight Beta 1 uses the approved city-facing layout in server-rendered Wagtail templates. The HomePage owns city branding, optional logo/hero images, introduction and contact information. Child ServicePages own guidance, HTTPS handoffs and contact/FAQ content. Wagtail's existing revisions and editor/moderator workflow govern these fields. The shared navigation, resident task finder and title search query live/public pages under the site's root; public meeting queries require `published=True`. Meeting series filters use actual public titles because no board field is supplied by the source contract. The small local script enhances the phone menu; forms and links operate without JavaScript. No third-party client scripts or city credentials are used.

The public meeting page presents the approved release and text-document links. Separate agenda, packet and minutes routes expose only the allowlisted approved native text; provenance is expandable. Withdrawal invalidates those routes as well as playback and discovery. Public assets are collected from `website/static/website` and included in the source offer. Uploaded city imagery uses existing Wagtail media storage; referenced originals and all published editorial fields are included in the hashed public export. A consistent full backup also includes Wagtail media, portal database and private release files.

The Wagtail site is a separate public presentation service. The native runtime remains private and exposes `POST /desktop/v1/portal/bundle` to an authenticated publisher with both Meetings and Records permissions. The publisher supplies an explicit approval, selection UUIDs and expected release hash. The runtime reads the canonical public Meetings archive and meeting, Station recording metadata, and Records request, document, current approval, completed artifacts and latest managed release copy. It verifies the selected release bytes and returns a versioned ZIP containing only whitelisted public meeting text, identifiers, hashes and the selected release bytes. The runtime audits the authorization. Records request text, publication payload, private originals, file paths and session proof are not bundled.

The portal streams from a configured trusted origin using a server-side proof file. It validates the ZIP, identities, paths, bounds and hashes before an atomic projection update. An explicit authenticated withdrawal hides the meeting and release; failed source reads do not withdraw. Approved bytes reside in a private file directory, outside public media, and are served only through a published-status and hash-checked streaming route. MP4 playback supports byte ranges. `export_public` includes those same approved bytes and a hash manifest. Public pages and the synthetic PrimeGov adapter remain independent of the native bridge.

The public source ZIP includes portal source and the bridge and mount files when present in a repository checkout. The repository source offer and operator obligations are described in README. This design does not provide a public write endpoint or a separate authentication provider.
