# Townlight API Module Specification

Status: future implementation specification
Source: `C:/Users/scott/Downloads/CivicAPI and CivicRegWatch modules.docx`

## Purpose

Townlight API is the unified public-read gateway over structured,
human-approved, published data generated by Townlight modules. It is the
city's outward API: rate-controlled, versioned, cited, and governed by the
city.

Townlight API does not scrape city data, wrap vendor APIs, aggregate data the city
does not own, or provide write operations. It publishes only approved
Townlight-generated public records.

## Product Promise

Developers, journalists, researchers, oversight agencies, neighboring
municipalities, and residents should be able to access a city's published
operational data through one documented, versioned REST API with a consistent
response envelope and provenance on every record. No record appears unless a
human explicitly approved its publication in the originating module.

## Non-Goals

- No records without a human approval publication gate.
- No staff-only, closed-session, privileged, exempt, or PII-containing records.
- No write operations.
- No replacement for module staff interfaces or systems of record.
- No third-party government API aggregation.
- No legal, policy, or compliance interpretations.
- No live intra-module data flows in v0.1.x.

## Architectural Position

Townlight API is a consuming module. It depends on Townlight Core and on publication
contracts from originating modules. Modules never depend on Townlight API, and
Townlight Core never depends on Townlight API.

Townlight Data remains responsible for bulk dataset packages and CKAN-oriented open
data publishing. Townlight API provides real-time, record-level API access to
approved transactional records.

## Publication Gate

No record reaches Townlight API without a named human publication action in the
originating module, recorded in that module's audit log.

Initial publication gate contracts:

| Module | Gate Event | Gate Actor | Records Published |
|---|---|---|---|
| Townlight Meetings | Minutes adopted + archive published | City Clerk | Meetings, agendas, adopted minutes, votes, action items |
| Townlight Records | Response marked fulfilled + released | Records Officer | Released public records metadata |
| Townlight Permitting | Permit intake accepted as public record | Permit Clerk | Permit intake records without personal applicant data |
| Townlight 311 | Service request closed + marked publishable | Department lead | Closed service requests with address anonymized |
| Townlight Budget | Hearing packet approved for public release | Finance Director | Budget line summaries and approved narratives |
| Townlight Contracts | Contract marked public record | Clerk / Legal | Contract registry entries |
| Townlight Grants | Grant compliance calendar published | Grant Administrator | Grant opportunity and compliance summary |
| Townlight Data | Publication plan approved | IT / Clerk | Dataset packages prepared by Townlight Data |
| Townlight Notice | Notice posted | City Clerk | Statutory public notices |
| Townlight Code | Ordinance adopted | City Clerk | Adopted ordinances and code sections |

Modules without a publication gate cannot contribute records to Townlight API.

## Publication Record

Originating modules write publication records into their own schemas and emit a
publication event to Townlight API's ingest queue.

Publication record fields:

- `publication_id`
- `source_module`
- `source_record_id`
- `record_type`
- `published_at`
- `published_by`
- `public_payload`
- `payload_hash`
- `schema_version`
- `effective_date`
- `retracted_at`
- `retracted_by`
- `retraction_reason`

Retraction removes a record from Townlight API responses but does not delete the
originating publication record or audit history.

## Response Envelope

Every response uses the same envelope:

```json
{
  "data": [],
  "meta": {
    "total": 147,
    "page": 1,
    "page_size": 25,
    "source_module": "civicclerk",
    "record_type": "meeting",
    "schema_version": "1.0"
  },
  "citation": {
    "city": "City of Longmont, Colorado",
    "source_module": "civicclerk",
    "record_type": "meeting",
    "published_at": "2026-04-29T14:22:00Z",
    "published_by_role": "City Clerk",
    "payload_hash": "sha256:a1f3...",
    "api_version": "v1"
  }
}
```

`published_by_role` is a role label, never a person name or ID.

## Authentication And Rate Limiting

Townlight API uses API keys for elevated access. Keys are issued by city admins,
hashed at rest, and fully audit-logged.

| Tier | Default Rate Limit | Intended For |
|---|---:|---|
| Public | 60 requests/minute, 10,000/day | Open unauthenticated access |
| Developer | 300 requests/minute, 100,000/day | Civic app developers |
| Research | 600 requests/minute, unlimited/day | Researchers and journalists |
| Institutional | Configurable | Neighboring cities and agencies |
| Internal | No limit | Townlight internal modules |

Rate-limit headers accompany every response. Violations return `429` with
`Retry-After`.

## Endpoint Surface

All endpoints are versioned under `/api/v1`.

- `GET /api/v1/health`
- `GET /api/v1/catalog`
- `GET /api/v1/catalog/{record_type}`
- `GET /api/v1/meetings`
- `GET /api/v1/meetings/{id}`
- `GET /api/v1/meetings/{id}/minutes`
- `GET /api/v1/meetings/{id}/votes`
- `GET /api/v1/meetings/{id}/action-items`
- `GET /api/v1/ordinances`
- `GET /api/v1/ordinances/{id}`
- `GET /api/v1/permits`
- `GET /api/v1/permits/{id}`
- `GET /api/v1/service-requests`
- `GET /api/v1/service-requests/{id}`
- `GET /api/v1/contracts`
- `GET /api/v1/contracts/{id}`
- `GET /api/v1/grants`
- `GET /api/v1/grants/{id}`
- `GET /api/v1/notices`
- `GET /api/v1/notices/{id}`
- `GET /api/v1/budget/narratives`
- `GET /api/v1/budget/narratives/{id}`
- `GET /api/v1/datasets`
- `GET /api/v1/datasets/{id}`
- `GET /api/v1/records`
- `GET /api/v1/records/{id}`
- `GET /api/v1/keys`
- `POST /api/v1/keys`
- `DELETE /api/v1/keys/{key_id}`

Endpoints for a module's record types mount only when the module is installed
and has at least one publication contract. Uninstalled modules return `404`;
installed modules with no published records return `data: []`.

## API Catalog

`GET /api/v1/catalog` returns available record types, schemas, producing
modules, publication-gate descriptions, city identity, current API version, and
publication policy.

## Data Model

Canonical tables in the `civicapi` schema:

- `civicapi.api_keys`
- `civicapi.rate_limit_buckets`
- `civicapi.request_log`
- `civicapi.publication_index`
- `civicapi.schema_registry`
- `civicapi.module_registry`

The publication index stores metadata and references. Source-of-truth record
content remains in originating module publication records.

## Sovereignty And Security

Townlight API is local-first. API keys and request logs stay on the city's network.
The city chooses whether to expose the API publicly through its own ingress.
Townlight API does not manage TLS, DNS, CDN, telemetry, or cloud services.

## Townlight Data Relationship

Townlight Data prepares bulk dataset packages and CKAN-oriented publication plans.
Townlight API provides real-time record-level API access. A city can run Townlight Data
without Townlight API, or run both.

## Dependencies

- Townlight Core: migrations, audit, city profile, auth helpers, provenance.
- Originating modules with publication contracts.
- Redis: rate limiting.
- Townlight Data: optional dataset endpoint producer.

## Prompt Library

Townlight API has no LLM-generated API responses. A future v0.2.x admin prompt may
generate a human-readable "City Data API Guide" from the live catalog.

## Test Matrix

- Publication event ingest and index population.
- Retraction propagation.
- Response envelope and citation block completeness.
- Payload hash verification.
- API key issuance, hashing, authentication, rotation, suspension, deletion.
- Rate limit enforcement and headers.
- Unauthenticated public-tier access.
- Admin-only key management.
- PII, closed-session, privileged, and exempt record exclusion.
- Catalog self-description accuracy.
- Empty dataset and uninstalled-module behavior.
- Air-gap behavior.
- Request log retention and rollover.
- Townlight Core compatibility matrix.

- Inter-module read contract protocol: shared database, internal HTTP API, or event queue.
- Whether `public_payload` is stored in originating modules or fetched live.
- Whether request logs are exposed in Townlight API admin or exported to Townlight Data.
- Final default rate-limit tiers.
