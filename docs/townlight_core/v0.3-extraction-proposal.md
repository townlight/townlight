# Townlight Core v0.3.0 Extraction Proposal

Status: proposed implementation plan

Governing ADR: `docs/architecture/ADR-0006-townlight_core-v0-3-extraction-scope.md`

Target repo: `Townlight/townlight_core`

## Purpose

Townlight Core v0.3.0 should extract the smallest shared primitives that active
post-foundation work already needs. The goal is not to build the full platform
roadmap. The goal is to make the next production-depth workflow safer,
more auditable, and easier to export without forcing every module to invent the
same metadata shapes.

## Recommended Scope

### 1. Audit Log Primitives

Candidate package: `townlight_core.audit`

Minimum public surface:

- `AuditEvent`
- `AuditActor`
- `AuditSubject`
- `AuditHashChain`
- `record_event(...)`
- `verify_chain(...)`

Required behavior:

- Events record actor, action, subject, source module, timestamp, and metadata.
- Each event can include previous hash and current hash.
- Verification detects modified event payloads, missing events, and broken
  previous-hash links.
- The package is storage-adapter friendly, but v0.3.0 may ship an in-memory or
  SQLAlchemy-neutral core before database ownership hardens.

Out of scope:

- User authentication.
- Role assignment.
- Final retention policy.
- Legal sufficiency determinations.

### 2. Source And Document Metadata Contracts

Candidate package: `townlight_core.provenance` or `townlight_core.sources`

Minimum public surface:

- `SourceReference`
- `SourceKind`
- `CitationTarget`
- `DocumentMetadata`
- `ProvenanceBundle`

Required behavior:

- Represents records request documents, meeting packet files, code sections,
  zoning parcels, GIS exports, local files, and generic URLs without requiring
  live connector runtime.
- Carries title, source system, source path/URL, captured timestamp, checksum,
  retention hint, sensitivity label, and citation locator.
- Can be serialized into export manifests.

Out of scope:

- Full document ingestion.
- Chunk storage.
- Hybrid search indexing.
- Permission-aware search.

### 3. Connector And Export Manifest Schema

Candidate package: `townlight_core.connectors.manifest`

Minimum public surface:

- `ImportManifest`
- `ExportManifest`
- `ManifestFile`
- `ManifestValidationError`
- `validate_manifest(...)`

Required behavior:

- Validates module name, module version, Townlight Core version, purpose, generated
  files, source files, byte sizes, checksums, and limitations.
- Supports file-drop imports, CSV imports, GeoJSON imports, and static export
  bundles.
- Does not imply live vendor sync.

Out of scope:

- Connector base class.
- Credential storage.
- Vendor-specific adapters.
- Write-back connector runtime.

### 4. City Profile And Onboarding Configuration

Candidate package: `townlight_core.city_profile`

Minimum public surface:

- `CityProfile`
- `DepartmentProfile`
- `DeploymentProfile`
- `ModuleEnablement`
- `load_city_profile(...)`

Required behavior:

- Loads a local YAML/JSON profile with city name, timezone, departments,
  enabled modules, default LLM provider, file-drop roots, and public-contact
  metadata.
- Validates that local-first defaults do not require outbound services.
- Supports the local demo deployment profile without becoming an installer.

Out of scope:

- Web onboarding wizard.
- Secrets management.
- SSO.
- Production deployment automation.

### 5. Export Bundle Utilities

Candidate package: `townlight_core.exports`

Minimum public surface:

- `ExportBundle`
- `BundleFile`
- `build_sha256sums(...)`
- `validate_bundle(...)`
- `write_manifest(...)`

Required behavior:

- Builds and validates `manifest.json` and `SHA256SUMS.txt`.
- Supports records-ready bundles generated by module code.
- Can run offline and can validate an export without the module server running.

Out of scope:

- PDF generation.
- Signed archival storage.
- E-discovery system integration.
- Public-records legal determinations.

## Release Shape

Recommended Townlight Core v0.3.0 PR sequence:

1. `audit` primitives and tests.
2. `sources/provenance` contracts and tests.
3. `connectors.manifest` schema and export utility tests.
4. `city_profile` local config model and tests.
5. Public API/docs/release-gate update.
6. v0.3.0 release PR, tag, and artifact verification.

Each PR should update README, README.txt, USER-MANUAL, CHANGELOG, landing page,
and public API examples where relevant. Every new public API must have direct
unit tests and a clean-wheel import smoke test before release.

## Consumer Impact

No module should pin to Townlight Core v0.3.0 until v0.3.0 is released. After
release, the first consumer should be the production-depth Townlight Meetings workflow
because it needs agenda packet provenance, notice evidence, audit events, and
records-ready export bundles.

Recommended consumer order:

1. Townlight Meetings production-depth workflow.
2. Townlight Records export/provenance alignment.
3. Townlight Code code-section export and ordinance handoff alignment.
4. Townlight Zoning GeoJSON/parcel import and zoning-answer provenance alignment.

## Why Not Auth/RBAC First

Auth/RBAC is necessary, but it encodes municipal policy: who can approve, who
can publish, who can see closed-session content, who can export, and how those
roles vary by city. Building that before the first production-depth workflow
would create a brittle abstraction.

Audit, provenance, manifests, and local city profile configuration are safer
first. They improve every module while leaving policy-heavy decisions to later
workflow evidence and ADRs.

## Done Definition For v0.3.0

Townlight Core v0.3.0 is ready only when:

- New packages are implemented with direct tests.
- Placeholder-package docs are updated so shipped/planned truth is clear.
- No new package requires outbound runtime calls.
- `scripts/verify-release.sh` passes end-to-end.
- The GitHub release publishes wheel, sdist, and checksums.
- The umbrella compatibility matrix is updated after release.
