Townlight for Windows 1.11.0.1

Townlight Windows 1.11.0.1 is a signed public beta, desktop build 1.11.0-1, with Townlight Utilities, Townlight Library, and Townlight Elections for staff-led public workflows.

  • Utilities sends a cited policy reply to the original 311 case and resident tracker.
  • Library publishes approved program announcements through Communications and links the archived revision in Records.
  • Elections publishes approved official checklists and same-URL corrections with retained Records versions.

Named staff permissions, a configured HTTPS portal, SMTP, Records, and host services are required. See the Utilities, Library, and Elections operator guide and the 311, Communications, and Parks operator guide.

Townlight Suite Manual

Using this manual

Townlight connects municipal workflows around retained sources, named staff and explicit human decisions. This suite manual explains setup, shared operating procedures and cross-product handoffs, including the bounded Access and Notice workflows. Set up Station during Townlight first run, or use Settings → Modules → Townlight Station on an existing installation. Standalone CivicCast remains a separate product.

Staff should start with First run and Connected workflows. Administrators should read Architecture, Configuration, Security and Recovery. Developers should use the API reference and per-product source contracts. Each acceptance result applies only to the artifact identified by its receipt.

First run

See the Windows acceptance summary for the exact installed checks and their scope.

Fresh installation

Run the signed Windows 1.11.0.1 MSI and use an empty database and a new Townlight profile for first run.

  1. Download the signed MSI, corresponding source, and checksums from the Windows x64 beta 1.11.0.1 release.
  2. Verify the MSI hash and Authenticode publisher before installation. See the Windows acceptance summary for the tested setup.
  3. Launch Townlight under the intended Windows account and choose storage folders. In setup, choose the full bundled profile labeled Townlight Inspections candidate. See component versions for its workspaces.
  4. Enter the city profile, time zone and contacts. Create the first named local administrator, sign in and choose protected backup storage. Continue without local AI is valid for the deterministic workflows.
  5. Select Run Health Check, then choose Finish setup; in System Health, if Prepare Records appears, choose it and follow its prompts, otherwise skip it.
  6. Create named staff through Settings. Import authorized sources using each product’s source library. All examples in this package are synthetic; they are not municipal authority.
  7. Set up Station during first run with the full profile or with Meetings and Records selected. On an existing installation, open Settings → Modules → Townlight Station → Set up meeting recording. Configure vision explicitly only if automatic photo drafting is selected.

Existing installation

Evaluating an upgrade. For an existing city, make and verify a backup before testing an upgrade. The 1.10.0.1 upgrade exercise confirmed retained data and the Library workflow. Elections after upgrade and final uninstall preservation remain unverified. Use an isolated copy for evaluation.

Daily workflow

Windows staff workflow guide covers Boards & Commissions, Contracts, Procurement, staff roles and linked records.

Sign in with your own named account. Confirm the selected workspace, open a saved record and check its source/version before editing. Save the work, record the intended review and inspect its audience. Use an explicit export or cross-product selection when a copy is required. Sign out when finished. Use the product manual for its field-level procedure.

Use your own named account and save before leaving a screen. A saved draft is durable; unsaved form text may not be. If a write has an unknown result, reopen its record before repeating it.

Read source jurisdiction, dates, citation, version and visibility. A copied source hash identifies exact bytes, not their legal applicability. If a source changes or permission is removed, resolve the source problem rather than substituting stale cached content.

Keep originals and derivatives separate. Review the intended audience before export. A public summary excludes private fields only through the applicable copy contract and your review. A renamed private packet is still private content.

Drafting, review, approval, attachment, export, fulfillment and publication are separate operations. A Townlight workpaper does not itself adopt law, issue a permit, impose a fine or release a records response. The responsible staff member records the applicable decision.

Connected workflows

Utilities replies to the original 311 case

An administrator registers the approved billing guidance policy and its version. A clerk opens the original 311 case, selects the cited policy, drafts the reply with protected notes, and explicitly approves the reply. The resident tracker shows the reply and citation, and the resident receives a matching email. Retry the same approved reply using its durable key. The workspace covers guidance and replies.

Library programs to Communications and Records

Staff save the program title, time, location, public description, and private notes, then a local administrator approves that version. A separate Communications review, approval, and scheduling step publishes the approved snapshot to the portal and sends it to opted-in subscribers. Link the published article revision to the program revision and verify its Records archive. Use this workflow for program announcements.

Elections checklists and corrections

A clerk drafts the checklist with jurisdiction, election, official source URL, and source version. An administrator designates an eligible official who differs from the author, who approves the exact revision. Separate Communications approval publishes it, and a correction is independently approved, uses the same URL, and retains separate immutable Records archives. Use this workflow for staff-approved checklists and corrections.

Named staff permissions, a configured HTTPS portal, SMTP, Records, and host services are required. Follow the department workflow guide for approval roles, retried delivery, links, and recovery.

Meeting capture to a Records response

  1. Meetings staff create the meeting and assign agenda items; save the canonical records.
  2. An authorized Station operator opens a one-use staff launch, chooses that meeting and a configured live input or managed file, then starts capture.
  3. Stop and wait for completed validated media. Inspect the content and provenance. Partial/failed attempts stay separate.
  4. Records-authorized staff explicitly attach the completed recording to an existing request. The receiver verifies bytes/hash and retains one locked private original, including on an identical retry.
  5. Records separately prepares any release copy, records release/redact/exempt decisions, approves exact response text, exports the response/package and fulfills the request. Capture and handoff do not publish it.

Download a private Records attachment

Authorized Records staff signed into the shared Windows workstation should open Records Requests and an existing saved request. Beside the private managed document, choose Download private attachment, then choose a new destination file or cancel. Townlight compares the byte count and SHA-256 before saving and reports the destination, count, and hash; protect the workstation copy as private Records evidence, with review and publication kept separate.

Legislation to cited staff guidance

Code imports a retained source and creates a proposal connection to actual Meetings evidence. Authorized staff record adoption, then a separate codification decision. Zoning uses the cited Code context with imported parcels and rules. Permitting and Inspections select permitted cited authority for reviewed workpapers. An import, draft or meeting motion does not replace the actual adoption/codification decisions.

Policy and land-use evidence to Records

Planning imports adopted policy revisions, including neighborhood applicability, and selects permitted Meetings/Zoning evidence. Staff save and review the exact analysis, then create the audience-specific snapshot. Planning initiatives/amendments retain their own history. Permitting and Inspections independently review their saved cases and prepare separate Records copies. Records rechecks the source/version/hash and owns the response release. Private notes and contact/property details must not be copied by relabeling a staff packet.

Shared foundation and recovery

Core provides shared contracts, named account/session support, ingestion/task helpers and coherent recovery. Supporting Notice and Access are included where selected. These relationships do not establish all 56 directed product pairs, universal vendor integration or unrestricted federation.

Shared Windows staff and approved portal publication

Shared Windows staff access and approved portal publication were introduced in 1.9.2.1 and remain available in 1.11.0.1; earlier test scope is version-specific. In shared mode, named Windows workstations use Meetings and Records through the city’s private HTTPS endpoint, while the host owns the database, managed files and Station capture. Townlight Clerk and Records Staff remain separate named roles; existing City Staff and Local Admin retain only the actions their previous permissions allow, and Code Staff gains no Meetings or Records authority. On a workstation, clerks can prepare council packets and send a reviewed correction; the host verifies copied files and records the operator. Station capture and administration remain on the host.

Fulfilling a Records request does not publish its contents. Staff must separately review and approve the exact council packet revision or eligible Records release copy for the portal. The shared host queues approved actions, retries after sign-out, outage or restart, and reports the confirmed status in Meetings. A packet correction replaces that packet only; packet and recording withdrawals are separate. Read the Windows staff workflow guide, shared staff guide, and Portal guide. The historical Windows 1.9.2.1 acceptance used synthetic data and a test portal on the physical host with a clean Windows Sandbox guest on the same PC; it does not establish two physical PCs, a different computer or account, or a production portal or city network.

Technical specifications

Runtime and storage

The 1.9.1.1 camera and microphone test remains evidence for that historical release. Windows 1.9.2.1 acceptance covers the shared staff workflows and same-machine cold recovery listed in its release summary. Its native shell uses Rust 2021, Tauri 2 and Microsoft WebView2; browser assets are JavaScript built with Vite 8.1.6. This describes the native desktop frontend; Station has a separate React operator, specified below or in its product manual. Canonical business workflows use bundled CPython 3.13.5, FastAPI, Pydantic, SQLAlchemy and Alembic, with PostgreSQL 17 / PostGIS and managed original files. Bundled dependency versions are recorded with the release evidence. Package minimum Python requirements can differ from the bundled executable; the metadata reference preserves both. No stack rewrite is implied by the beta label.

The native transport is fixed to loopback 127.0.0.1:15480; PostgreSQL uses the configured local runtime port (default 15432). Optional local model service defaults to 127.0.0.1:15434. Those are deployment defaults, not internet endpoints. The runtime has health, module and readiness endpoints; readiness is stronger than process existence. The task queue is the existing local Core task infrastructure, not an assertion that a separate Redis service is required for this desktop composition.

The default native profile is %LOCALAPPDATA%\CivicSuite; the historical directory name remains part of compatibility. Do not rename it to Townlight. A configured TOWNLIGHT_PROFILE_ROOT must be absolute. Local configuration and secrets live under that profile; protected managed files and database state must be backed up coherently. Source/runtime identity is distinct from a product’s display label.

Data and consistency

Each product retains the records described in its manual. The common desktop uses one canonical PostgreSQL-backed domain with product-owned tables/schemas and managed file storage. Station has a separate database and media store.

Versioned saves use expected prior revision identifiers where defined. Reopen and reconcile on conflict. Exact exports and handoffs use source IDs, current visibility, revision and SHA256. Review belongs to the saved revision and does not transfer silently to edited text. Database changes use the owning product’s migrations; a request or readiness check is not an authorization to mutate schema.

Capacity and platform statements

This beta has synthetic single-profile workflow evidence. It does not have a published benchmark for concurrent staff capacity, minimum RAM/CPU, large-source limits or a field SLA. Do not turn a developer machine’s specification into a supported minimum. The release download lists the exact MSI size; allow additional disk for extracted runtime, database, originals, exports, media and backups. Select equipment/storage after sizing those actual workloads.

The exact runtime payload lock records pinned files, sizes and hashes. The component metadata records shipped dependency declarations. These references are more precise than a manually copied dependency list. Third-party and historical license notices must accompany their matching payloads.

Station operator and media components

The native desktop frontend above is distinct from Station’s browser operator. The pinned operator package townlight-station-operator is version 0.1.0, using React/react-dom 19.1.1, TypeScript 5.9.2, Vite 7.3.7 and the React Vite plugin 5.0.2. Station serves its built assets through its own operator API. Its Python control/API package remains townlight-station 0.3.0, while its retained storage identity remains 0.1.0. These identities have different purposes and are not renumbered.

The separate pinned CivicCast-derived media engine uses Python/native GStreamer processing and bounded media children. It is not the standalone CivicCast application. Station’s control database, data root, service/configuration and update identity remain independent. This describes the current mixed stack; no runtime rewrite or CivicCast migration is implied.

Configuration and administration

Native deployment configuration

Use Setup, Settings and System Health for supported staff operation. Administrators provision folders, backup storage, named accounts and the city profile. Select inspections-preview for the bounded desktop composition, including Access, Notice, Boards & Commissions, Contracts, and Procurement. Station remains a separate service boundary. Do not use a standalone product’s demo server as a substitute for the installed workspace.

Technical deployments use TOWNLIGHT_PRODUCT_PROFILE, TOWNLIGHT_PROFILE_ROOT, DATABASE_URL, TOWNLIGHT_RUNTIME_PORT, PORTAL_MODE and the runtime-managed secret files. Treat database URLs and native session proofs as secrets. The installed native domain runtime explicitly refuses non-loopback binding. PORTAL_MODE=private is the accepted posture; changing it does not by itself commission an internet portal, authentication provider or reverse proxy.

The isolated documentation exporter sets a fictional profile and unusable synthetic database origin only to read schemas; those values are not deployment configuration. Keep deployment values in the intended process/account scope. An already-running process does not automatically inherit later environment edits.

Trusted local HTTP example

An administrator/developer can inspect an already-configured isolated runtime from a trusted local process. This PowerShell example reads the signed-in synthetic profile’s existing proof into memory; it does not create a user, seed a session, reveal the proof in output or bypass a permission check. Do not use real city data in development examples. A read response does not prove approval or publication.

$profilePath = Join-Path $env:LOCALAPPDATA 'CivicSuite'
$sessionPath = Join-Path $profilePath 'config\local-session.json'
$session = Get-Content -LiteralPath $sessionPath -Raw | ConvertFrom-Json
$headers = @{ 'X-Townlight-Session' = $session.session_hash }
Invoke-RestMethod -Uri 'http://127.0.0.1:15480/desktop/v1/meetings/station/catalog' -Headers $headers
Remove-Variable session, headers

A synthetic write with subsequent readback

This example demonstrates the existing Meetings HTTP contract in an isolated exercise. It is intentionally fictional. It does not start a service. Its authentication setup is included so it can be run independently under the signed-in synthetic account. If a write times out, inspect current records before repeating it.

  scheduled_start = '2026-11-05T18:00:00-07:00'

$meeting = Invoke-RestMethod -Method Post `

MCP and automation boundary

No direct product MCP server is exposed by the accepted Townlight desktop or Station boundary. Do not configure an invented townlight mcp command or assume an AI client has staff permissions. The integration surfaces for this beta are native IPC, the documented HTTP APIs, source bundle imports, exact exports and the existing Station CLI.

The bundled transcription code includes a TextFlowKit MCP adapter as a separate source capability. It offers job-based transcribe_media, get_transcript, list_jobs, get_job_status and export_transcript, and additional tools declared in that adapter. It uses stdio first and optional Streamable HTTP, with the MCP SDK as an optional extra. It is not automatically launched, authenticated as Townlight staff or accepted as a Townlight product MCP deployment. This documentation does not add such a service.

For a transcription client already provisioned separately, an illustrative tool call is:

{"name":"get_job_status","arguments":{"job_id":"synthetic-existing-job-id"}}

Use a job ID returned by that transcription service. This example does not create a Townlight record or bypass its review/Records handoff. The exact optional adapter tool signatures are supplied in the MCP source reference. Station meeting capture does not become live speech recognition because this optional donor adapter exists.

Backup recovery and maintenance

Save work and use Core’s canonical Backup Now before maintenance. That operation stops writers. Preserve the coherent profile/database/document backup and its receipt, then use Start to resume. A source export is not a full backup.

Use Restore Latest Backup through the supported controls. If the result says Restore needs service start, use Start, then Check, and reopen a known record. Do not repeat restore merely because services need to start. The Windows 1.6.0.1 Beta 1 fresh-install acceptance verified that a fulfilled request survived restore and a post-backup marker did not.

Keep Station’s dedicated database and media evidence together in its own backup. Core’s native-profile backup must not be assumed to include an external Station data directory. Stop writers during a coordinated backup. Preserve failed media attempts and logs.

On failure, record the time, selected composition, component/installer versions and exact message. Check System Health for stopped, starting, ready or failed dependencies. Use the existing Retry control after readiness; do not create duplicate business records to refresh a stale view. Share only a redacted diagnostic bundle. Preserve secrets, original evidence, recovery material and unrelated installations.

Set up and operate Station

Clerk and operator

  1. Install Townlight and complete normal first-run setup with the full Windows profile or a custom selection that includes Meetings and Records (Station is bundled). Finishing setup provisions the bundled recorder, a private database and Windows sign-in task. No PostgreSQL, Python or media-runtime installation commands are needed. Existing installations use Settings → Modules → Townlight Station → Set up meeting recording.
  2. Keep Windows signed in and the computer awake while recording. The recorder runs in that user’s device-access session, independently of the Townlight window. It is not a multi-user server or a full PEG station. Closing the recorder tab does not stop a recording.
  3. Sign in with an existing authorized staff account. From Meetings choose Open / reconnect to meeting recorder. Select a meeting and its agenda items. In input setup, find devices, choose one camera/capture device and one microphone, and save. Record a ten-second input test, then play it to check the picture and sound; the meter responds during playback. This test clip is temporary and is not a canonical meeting record. Windows camera/microphone privacy settings and exclusive device use still apply. Configured UDP MPEG-TS input remains supported.
  4. Start the meeting recording. The default duration limit is eight hours, with a 64 GiB file limit and at least 1 GiB reserved disk space. Admission estimates the configured duration and bitrate. Free space is monitored while recording; low space or a limit requests a graceful stop and displays the reason. These are configured limits, not a claim that every eight-hour meeting has been tested. Plan space for the recording, its Records copy and backups. Sleep, sign-out, power failure and unavailable hardware can interrupt capture.
  5. An open operator page renews its fifteen-minute session against the current Townlight staff authority. Sign-out, revoked permissions and the underlying staff-session expiry still take effect. Reopen from Townlight to reconnect to an existing recording; reconnect never starts a second recording. Select Stop recording to drain and finalize the file.
  6. After completion, an authorized Records user selects a request and explicitly attaches the recording. Records streams a separate managed copy and verifies SHA-256, size and provenance; files up to 64 GiB are accepted subject to available space. Attachment is not public release. Review, redaction and publication remain separate Records decisions.

Administrator and recovery

Station setup uses bundled native dependencies and its existing pinned CivicCast media implementation; it never starts or changes CivicCast or CivicCast Lab. The per-user logon task owns a separate PostgreSQL instance on loopback port 15435; Station’s API listens only on 127.0.0.1:8756. Townlight’s existing staff authority remains on its configured Suite origin. Protected settings and database credentials remain in the recorder data directory, under the selected city data location. Setup refuses unrelated nonempty storage or an unrelated task with the same name. Retry setup after correcting readiness errors; inspect the private background, PostgreSQL, API and worker logs when needed.

Use Check recorder readiness, Back up Station, and Restore Station backup in Settings → Modules. Finish queued and active recordings before backup or restore. Backups contain a PostgreSQL dump, recording/ingest files, saved source choices and a SHA-256 member manifest; they omit credentials and native executables. Restore verifies the members, creates a pre-restore recovery copy, and restores into this installation’s separately protected database. Recheck input selection afterward. A Suite backup includes a coherent Station backup when paired; it does not copy the running Station database or its secrets. Suite restore preserves that live private directory and applies the included Station backup separately.

Station live and recorded delivery

Station now offers two explicit delivery paths. During a live recording, staff may select an administrator-configured encrypted SRT feed to the separate CivicCast product. The PEG operator controls local cable take-to-air. After completion, staff may approve an upload copy to the Station-configured YouTube account, select its title and visibility, and inspect the durable receipt. The private canonical recording and existing Meetings → Station → Records handoff remain independent.

These paths reuse the pinned CivicCast media and YouTube client code. A separate sender isolates network backpressure from capture, and a separate upload worker prevents long uploads from blocking recording. YouTube starts no live broadcast here. Standalone CivicCast has separate installation, identity, storage and operator control.

Administrators run the explicit Station schema4 migration and provision Station-only OAuth and SRT pairing credentials. Existing component versions are retained. Preparation failures can be explicitly retried; uncertain external uploads require manual reconciliation and are never silently duplicated. No real credentials or external video publication are used in synthetic development acceptance.

See the Station manual delivery section for full staff steps, architecture, configuration, API request examples, permissions and recovery. Existing eight-product workflows are unchanged; their accepted evidence is retained rather than presented as a new run.

Townlight Budget (Windows Suite)

  1. In Staff > Budget, enter fiscal year and use Import budget CSV with header department,account_code,description,prior_year_amount,proposed_amount and dollar amounts such as 1234.56. Correct any row errors and reimport. An invalid file creates no revision.
  2. Select the saved revision, verify totals, and Save finance review using a named staff account with Budget access.
  3. Download hearing attachment to create budget-revision.txt. In Meetings, open the saved hearing, assign the agenda item, include that exact attachment as a public candidate, preview, and approve the public packet.
  4. In Capture a motion, supply hearing meeting ID and agenda item ID. Record the council roll-call vote.
  5. As a clerk or local administrator, select the saved evidence in Budget and record the carried result and resident summary.
  6. With a configured publisher, a local administrator selects Queue adopted budget for publication and checks the public Portal Datasets view for the CSV and summary.

Townlight Grants (Windows Suite)

  1. In Staff > Grants, enter the opportunity title, funding area, deadline, project name and city need. Select the adopted Budget revision, signed Contract and saved Records request from the lists. Confirm all three before creating the case.
  2. Open the case and save an assignment to an active named city staff member or local administrator. Read the triage, eligibility factors and application outline as staff workpapers.
  3. Record the review note. After the city confirms the award, record the award reference, amount in cents, report due date and reporting frequency. Check the generated calendar against the signed award.
  4. Save the report completion note, close the case and select Download verified archive. Reopen the case to retrieve the same SHA-256-verified JSON and check the three source references.

Grants records staff decisions and timestamps. Funder applications, awards and reporting submissions take place outside Townlight.
