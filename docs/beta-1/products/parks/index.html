Parks and recreation workflows

Resident booking and program registration

  • Public facility and program catalogue, availability, booking and registration forms.
  • Facility reservations with recurrence, setup/cleanup buffers, closures/blackouts, rescheduling and cancellation.
  • Resource and session rows are locked in the same transaction as overlap checks and occupancy writes.
  • Recurrences are all-or-nothing and lock in stable order.

Private households and participants

  • Households, participants, and minor/accessibility/contact data stay private.
  • Public pages expose catalogue and availability only.
  • Public pages do not expose household, participant, minor, accommodation, contact, or private tracking details.

Programs, capacity and waitlists

  • Programs and sessions with eligibility, capacity, enrollment, waitlists and promotion.
  • Private rosters and idempotent attendance check-in.

Fees, offline ledger and optional Stripe

  • Fees, deposits, refunds and reconciliation in integer cents with explicit currency.
  • Offline payments and refunds are recorded in an append-only ledger with staff actor and reference.
  • Optional hosted Stripe Checkout adapter for online payment. A city must configure its own Stripe account, and no live charge has been verified.
  • Card data does not enter Townlight. Provider return URLs are not payment proof; the host retrieves and verifies provider transaction, amount, currency and obligation identity before recording a ledger payment.

311 and Communications

  • Maintenance links create real 311 requests with durable idempotency, actual location/photo bytes, and returned 311 request identity.
  • Explicitly approved public closures and program descriptions can become Communications source snapshots.

Records and Data

  • Records private ZIP archive and readback.
  • Approved aggregate Data export.
  • Records archive access remains permission-controlled.
  • Data exports exclude participant, contact and accommodation details.

Operator/admin roles, privacy, and configuration

Roles and access

Existing roles remain local-admin, city-staff, and clerk. Records archive permission is separate. Parks reuses the shared command/session proof and allocation-receipt approach used by 311 and Communications.

A standalone main.py is retained as a foundation/demo entry point. It is not the full Suite authentication path, not a normal installer, and not the ordinary city-staff deployment route. Ordinary city staff should use the signed Windows suite installer.

Privacy, concurrency and recovery

Private tracking links, CSRF checks and session ownership protect resident commands. Durable command identities prevent replay duplication; queued work is not confirmed until the host applies it.

Back up the database, managed files, portal inbox, profile encryption keys and publisher queue together. Restart must reopen durable requests and resume known-safe jobs without duplicates. Payment and refund intents persist across restart; ambiguous provider outcomes are reconciled before retry.

Configuration

Target Windows, Python >=3.11. Package townlight-parks==0.2.0; import townlight_parks; Core target townlight-core==1.3.0.dev2.

For development, install Core from the pinned townlight/core git commit 2f6ba9be4a95e3772dc47a3682ac780c5283b626. The Core package requirement is not a promise of PyPI availability.

Database schema: townlight_parks. Production bootstrap is False; tables are created only through explicit programmatic migrations (migrations.upgrade(engine), then migrations.assert_ready(engine) via the package migrations module).

Configure database credentials and hosted payment secrets outside source control. Do not place secrets or card details in configuration files, logs, or the repository.
